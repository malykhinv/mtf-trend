# Playbook: эффективные, экономичные прогоны бэктестов

> Назначение: воспроизводимый метод, как быстро и дёшево гонять исследование
> торговых гипотез на 1m-данных (сотни символов, десятки тысяч событий), не
> сжигая время и память. Написано так, чтобы это мог применять другой ИИ.

## 0. Главный принцип: BUILD-ONCE, ANALYZE-MANY

Разделяй работу на два слоя:

1. **BUILD (дорого, редко):** один проход по кэшу символов, который симулирует
   сделки и пишет **обогащённый parquet** — по строке на сетап, со ВСЕМИ
   кандидатами-метриками и ВСЕМИ вариантами выхода. Занимает минуты.
2. **ANALYZE (дёшево, часто):** любые фильтры, стратификации, отборы, метрики
   робастности — **на сохранённом parquet, без пересимуляции**. Занимает секунды.

**Пересобирай только когда меняется ДЕТЕКЦИЯ сетапа или нужна НОВАЯ сырая метрика
из баров.** Фильтрация по размеру пампа, порогам, комбинациям, отбор моделью — это
всегда ANALYZE на parquet, НЕ новый build.

Если ловишь себя на пересборке ради «а что если порог 0.6 вместо 0.5» — стоп: это
слайс на parquet.

## 1. Что кладём в BUILD-проход

- Все **варианты выхода сразу** (сетка стоп×цель: wick/body/range × perehai/2R/3R/
  trail) — по одному net-столбцу на вариант. Тогда «какой выход лучше» — слайс.
- Все **кандидаты-метрики сразу** (геометрия, поток, размер сделки, свечные) —
  даже те, в которых не уверен. Добавить метрику дёшево В проходе, дорого — отдельным.
- **Причинные и пост-входные метрики раздельно** и явно помеченные (пост-входные —
  только для изучения поведения, НЕ для фильтра входа: это look-ahead).
- Ключи для стратификации: `mo` (месяц), `week`, `symbol`, `hour`/сессия.

## 2. Что НЕ кладём в build (оставляем на analyze)

- Пороговые фильтры, отбор по квантилям, комбинации условий.
- Отбор моделью (WFA), ранжирование.
- Метрики робастности (они считаются из net-столбцов на parquet).

## 3. Инженерные паттерны (что делает проход быстрым)

- **Один симулятор в ядре.** Никогда не пиши sim-loop заново в скрипте. Переиспользуй
  `simulate_long_path` (вход next-open+слиппедж, стоп-до-трейла, честные издержки).
- **Numpy-массивы, не объект-на-свечу.** Грузи бары символа как
  `ts/open/high/low/close/vol` через `.to_numpy(float)` один раз.
- **Группируй по символу, грузи символ ОДИН раз, итерируй все его события.**
  Не перезагружай файл на каждое событие.
- **`searchsorted` для позиционирования события в баре**, а не поиск по времени.
- **Причинный ATR/индикаторы считаем один раз на символ** (кэшируй в проходе).
- **Прогресс-логи с `flush=True`** каждые N символов (иначе фоновый прогон «немой»,
  а буфер невидим). Печатай `k/total symbols, N outcomes so far`.
- **Фоновый запуск** длинных build-ов (`run_in_background`); не блокируй сессию,
  получай уведомление по завершении. Выход пиши в файл, читай grep-ом.
- **Пиши parquet, не CSV** (быстрее, типизировано, компактно).

## 4. Дисциплина робастности (всегда, на каждом «плюсе»)

Единая функция-сводка на массиве net-доходностей: EV, winrate, median, PF, а также
обязательные анти-самообман метрики:
- `top_removed_to_negative` — сколько % топ-сделок удалить до EV≤0 (0% = несёт хвост).
- `ev_excluding_best_month` (**exBest**) — знак должен держаться без лучшего месяца.
- доля положительных месяцев / недель.
- **концентрация PnL по символам** (top-5 символов / общий PnL; >100% = остальные
  убыточны = лотерея, НЕ эдж).
- деконцентрированный EV (среднее по символам равным весом).

Любой «headline-плюс», не проходящий exBest И концентрацию — мираж.

## 5. Причинная дисциплина (иначе всё враньё)

- Фичи фильтра ВХОДА считаются только по барам ≤ бар решения. Пост-входные фичи
  (что было ПОСЛЕ входа) — это look-ahead, фильтром входа быть не могут.
- Сильный Cohen's d проверяй leak-safe недельным WFA: он часто оказывается
  артефактом выхода (меняет знак при смене определения выхода = не сигнал).
- Пороги морозятся на development; OOS — единственный арбитр, к нему НЕ подстраиваться.
- Валидируй против blind и shuffled/permutation контролей.

## 6. Ориентиры по компьюту

- Загрузка символов доминирует над симуляцией. ~600 символов + ~2–3k сетапов ×
  ~10 симуляций ≈ 5–10 мин. Добавить метрику в проход — почти бесплатно; добавить
  символьную загрузку — дорого.
- Если прогон >30 мин без прогресса — почти всегда O(n²) или отсутствует кэш
  загрузки. Убей, перепиши на «один проход, загрузка на символ».
- Держи `tmp/` чистым (выхлопы прогонов — мусор); скрипты-однодневки — в scratchpad,
  переиспользуемые билдеры — в пакет стратегии.

## 7. Анти-паттерны (не делай)

- ❌ Пересборка ради смены порога/фильтра.
- ❌ Копипаст sim-loop в каждый скрипт (дрейфует от ядра, плодит баги).
- ❌ Перезагрузка файла символа на каждое событие.
- ❌ Радость по headline-EV без exBest + концентрации по символам.
- ❌ Пост-входная фича как фильтр входа.
- ❌ `print` без `flush` в фоновом прогоне.
- ❌ Вывод с кириллицей без `PYTHONIOENCODING=utf-8` (падает на cp1252-консоли).

## 8. Скелет прохода (псевдокод)

```python
lat = read_lattice(cols=[...])                  # только нужные колонки
for symbol, g in lat.groupby("symbol"):         # символ — один раз
    ts,o,h,l,c,vol = load_arrays(symbol)         # numpy, один раз
    atr = causal_atr(h,l,c)                       # индикаторы — один раз
    for row in g.itertuples():                    # события символа
        i = searchsorted(ts, row.snapshot_ms)
        setup = detect(...)                        # причинная детекция
        if not setup: continue
        for stop in STOPS:                         # ВСЕ варианты в проходе
          for tgt in TARGETS:
            rec[f"net_{stop}_{tgt}"] = simulate_long_path(...).net_return
        rec.update(all_candidate_metrics)          # ВСЕ метрики в проходе
        rows.append(rec)
write_parquet(rows)                                # затем — только analyze
```

Итог: **тяжёлый проход один раз, потом мгновенные слайсы** с обязательной проверкой
робастности и причинности.
